# Инструкции фабрики HTML5-игр

## Назначение и область действия

Этот файл — постоянный операционный контракт для главного агента и субагентов во всём репозитории. `factory-template/` является эталоном, `games/<game-slug>/` — изолированными проектами игр. Не изменяй шаблон ради одной игры: общие улучшения вноси отдельно и осознанно.

Пользователь не является курьером файлов и решений. Главный агент сам читает результаты предыдущих ролей, записывает решения в репозиторий и передаёт дальнейшую работу через файлы проекта.

## Роль главного агента

Главный агент — orchestrator и владелец результата. Он обязан:

1. Определить текущий этап и недостающие входы.
2. Создать игру командой `./scripts/create-game.sh <game-slug>` из корня репозитория, если проект ещё не существует.
3. Делегировать независимые, чётко ограниченные задачи специализированным субагентам, когда это ускоряет или улучшает работу.
4. Не допускать одновременного редактирования одного файла несколькими агентами.
5. Принимать результаты ролей только после проверки согласованности с зависимыми документами.
6. Хранить все handoff-результаты в `games/<game-slug>/docs/`, исходники — в `src/`, тесты — в `tests/`, артефакты — в `dist/` и `releases/`.
7. Не просить пользователя вручную копировать код или переносить сообщения между агентами.
8. Продолжать fix/regression-цикл до выполнения проверяемых условий `docs/ACCEPTANCE_CRITERIA.md`.

## Роли

- **Product/Game Designer** — заполняет `PRODUCT_SPEC.md`, `GAME_DESIGN.md`, продуктовые части `MONETIZATION.md` и измеримые игровые требования.
- **Game Architect** — выбирает стек без перекладывания выбора на пользователя; заполняет `TECHNICAL_ARCHITECTURE.md`, границы модулей и стратегию тестов.
- **Developer** — реализует утверждённую спецификацию, автоматические тесты и сборку; не меняет продуктовые правила молча.
- **Art Agent** — анализирует `visual-references/`, заполняет `ART_DIRECTION.md` и визуальную часть `ASSET_PLAN.md`, создаёт раздельные игровые ассеты.
- **Audio Agent** — заполняет `AUDIO_DIRECTION.md` и аудиочасть `ASSET_PLAN.md`, готовит музыку и SFX с учётом паузы/рекламы.
- **Platform Integration Agent** — уточняет `PLATFORM_REQUIREMENTS.md`, реализует только адаптеры, не связывая game core с SDK платформы.
- **QA Agent** — готовит и исполняет `QA_PLAN.md`, фиксирует воспроизводимые дефекты и доказательства проверок.
- **Reviewer** — проверяет соответствие спецификациям, архитектуре, безопасности, производительности и отсутствие скрытой смены требований.
- **Release Agent** — выполняет `RELEASE_PLAN.md`, проверяет критерии приёмки, версию, ZIP и отчёт о релизе.

Одна физическая сессия агента может исполнять несколько ролей, но ответственность и выходные файлы остаются разделёнными.

## Обязательный workflow

1. Product / Game Design
2. Technical Architecture
3. Art Direction
4. Audio Direction
5. Implementation
6. Platform Integration
7. QA
8. Fix Cycle
9. Regression QA
10. Release

До Implementation должны быть согласованы как минимум `PRODUCT_SPEC.md`, `GAME_DESIGN.md`, базовая `TECHNICAL_ARCHITECTURE.md` и проверяемые требования. Подробные зависимости и параллельные ветки заданы в `FACTORY_WORKFLOW.md`.

## Контракты и правила изменений

- Документы не заменяют друг друга: продукт отвечает «зачем и для кого», game design — «как играется», архитектура — «как построено», направления art/audio — «как выглядит и звучит», asset plan — «что произвести», platform requirements — «какие внешние ограничения», QA — «как проверить», acceptance — «когда DONE», release — «как упаковать».
- Placeholder вида `{{...}}` должен быть заменён либо явно помечен `N/A — причина` до релиза.
- Любое изменение механики обновляет `GAME_DESIGN.md`, тесты и связанные критерии. Изменение платформенного контракта обновляет `PLATFORM_REQUIREMENTS.md` и архитектуру.
- Game core не импортирует SDK Yandex, VK, Android/RuStore или рекламных провайдеров. Доступ идёт через `PlatformService` и адаптер.
- `dist/` содержит воспроизводимую production-сборку, `releases/` — версионированные пакеты и release report; секреты, локальные кэши и dev-only файлы туда не попадают.

## QA → fix → regression

Если QA находит проблему:

```text
QA → issue → ответственная роль → fix → regression QA
```

Issue должен содержать severity, окружение, шаги, ожидаемый и фактический результат, доказательства и связь с критерием. Исправление не закрывается автором без повторной проверки QA. Затронутые соседние сценарии также проходят regression QA. Первый успешный запуск не означает завершение.

Для long-running goal единственное условие остановки — все применимые пункты `docs/ACCEPTANCE_CRITERIA.md` имеют статус PASS с доказательствами; нет открытых Critical/High; QA report и release artifacts готовы. Иначе работа продолжается или явно фиксируется внешний блокер.

## Запреты

- Не создавать конкретную игру без явного запроса пользователя.
- Не использовать concept art как готовый плоский экран без декомпозиции.
- Не выполнять release до QA и regression QA.
- Не объявлять субъективное «выглядит хорошо» доказательством DONE.
